# 排查手册：命中率不达预期

> 按顺序做，每步都有可执行的命令或读数。**先排除自己的前缀，再怀疑服务端。**

## 0. 先算账：缓存到底划不划算

```
不缓存：  N × 输入价 P
用缓存：  N(1-h) × 写入价 W  +  N h × 读取价 R
盈亏平衡命中率 h* = (W − P) / (W − R)
```

以写入 1.25P、读取 0.1P 为例：`h* = 0.25 / 1.15 ≈ 22%`。

**结论：一段前缀只要会被复用两次以上（实际命中率通常远超 22%），就划算；只调用一次就开缓存，纯亏 25%。** 所以优化顺序永远是：先确认"同一段前缀会被重复用"，再调断点位置。

## 1. usage 里两个缓存计数是不是都为 0

都为 0 ⇒ 本轮完全未命中。不要先怀疑网络或服务端，先做第 2 步。

一个非 0 一个为 0 ⇒ 只写不读（第一个请求的正常状态）或只读不写（说明断点没覆盖到你以为的那段）。看第 3 步。

## 2. 逐字节比对前缀

把两次请求的原始 prompt 按"工具定义 / 系统提示 / 消息列表"三段切开，分别算摘要：

```bash
# PREFIX_FILE 是切出来的那一段原始文本（不要经过格式化）
sha256sum "$PREFIX_FILE"
```

两次摘要不一致 ⇒ 前缀真的变了。常见来源：

- JSON 键顺序不稳定（序列化库默认不保序）；
- 工具定义里嵌了时间、版本号、随机 id；
- few-shot 示例顺序随机；
- 末尾多/少一个换行。

## 3. 前缀里有没有易变内容

逐条 grep 你的 prompt 模板：

```bash
grep -nE 'now|time|date|uuid|random|seed|request.?id|session' prompt_template.txt
```

命中任何一条在前段的内容，就是它。把它们挪到消息段末尾。

## 4. 长度够不够

对照 `references/providers.md` 的最小可缓存长度。前缀短于该值 ⇒ 静默不缓存，计数恒为 0。

检查方法：数一下稳定前缀的词元数（多数 provider 的返回里会带输入词元总数，前缀长度可以按同一分词器粗估）。

## 5. 是不是并发首批

一次性并发 N 条时，只有最先开始响应的那条能写入缓存，其余 N−1 条全部未命中。

改法：**先发一条预热，等它返回，再并发其余。**

## 6. 过期

Anthropic 默认 5 分钟，且从**请求开始**计时——不是从响应结束。批量任务中间隔久了，自然全 miss。要么缩短间隔，要么接受"每轮第一条未命中"。

## 7. 五个真实翻车形态

| 形态 | 现象 | 根因 | 改法 |
| --- | --- | --- | --- |
| A 时间戳进了系统提示 | 命中率恒 0 | 每轮前缀都不同 | 时间挪到用户消息末尾 |
| B 工具描述带版本号 | 升级后命中率骤降 | 整个工具段变了 | 版本号移出 schema |
| C 换了 provider 还留 `cache_control` | 一直 0，不报错 | 对方没有这个参数 | 删掉，按对方默认行为走 |
| D 前缀刚好差一点点长度 | 一直 0 | 低于最小可缓存长度 | 把 few-shot 并进稳定前缀 |
| E 命中率 60% 但账单变贵 | 看着"有优化" | 命中的只是短系统提示，主体在反复写入 | 把大块资料挪进稳定前缀，别每次重写 |

## 8. 上线前的检查清单

1. 同一段前缀会被复用 ≥2 次吗？
2. 断点在稳定段末尾、后面还有可变内容吗？
3. 前缀里有时间、随机数、随机顺序吗？
4. 前缀长度够最小可缓存长度吗？
5. 批量任务是"先预热再并发"吗？
6. 看过账单而不是只看命中率吗？
