# LLM 前缀缓存工程

前缀缓存能把重复的前半段输入按"读取价"计费，通常比普通输入便宜一个量级。它失效的方式也很单一：**只要前缀里有一处变了，从那一处往后全都不命中。** 这份 Skill 就是把这件事写成可执行的动作。

## 三条铁律

1. **缓存按"从头开始的连续前缀"匹配。** 只有完全一致的前缀才命中；前缀中任何一处改动，都让该处之后的内容重新计费。
2. **稳定内容放前面，易变内容放后面；断点打在稳定段的末尾。**
3. **命中率必须用 provider 返回的 usage 字段自证。** "感觉变快了"不算证据，"本地算的"也不算。

## 1. 两个口径，别混用

```
词元级命中率 = 命中词元 / (命中词元 + 未命中词元)
请求级命中率 = 至少命中过一次的请求数 / 总请求数
```

- **词元级低** ⇒ 前缀不稳：有易变内容混进了前段，或前缀没跨过最小可缓存长度。
- **请求级低** ⇒ 断点位置不对、长度不够，或一次并发把首批全打成了未命中。

**两个一起看。** 请求级高而词元级低，说明每次只命中了很短的一段（比如只有系统提示），主体资料仍在重复计费——这是最常见、也最容易被"命中率 60%"骗过去的状态。

## 2. 前缀模型：改了什么，就从哪儿开始失效

前缀顺序固定为：**工具定义 → 系统提示 → 消息列表**。工具定义排在最前，意味着它一动，后面的系统提示和全部消息一起失效。

| 你改了什么 | 从哪儿开始失效 |
| --- | --- |
| 工具名、工具描述、参数 schema | 工具段及其后的**全部**内容 |
| 系统提示的任意一个字 | 系统提示段及其后的全部 |
| 增删图片、切换工具选择策略 | 消息段及其后的全部 |
| 把当前时间、请求编号、随机种子放进前段 | **每次都不命中** |
| JSON 字段顺序变了、列表重排了 | 等价于内容变了，**前缀全变** |

> 最后两行是最隐蔽的：文本看着"差不多"，但前缀匹配是逐字节的。

## 3. 三段式 prompt 结构

```
[稳定前缀]  系统提示 + 工具定义 + few-shot + 固定输出格式约束   ← 断点打这里
[半稳定]    当天/当会话才变：项目背景、用户画像、检索到的大块资料  ← 可选第二个断点
[易变后缀]  本轮用户输入、当前时间、临时状态                    ← 绝不加断点
```

**只追加，不改写。** 想"更新"前面的内容时，在后文追加一条修正说明，而不是回头改前缀——改一次前缀，等于把之前攒的缓存全部作废。

## 4. 断点放置规则

1. 断点放在**"跨请求不变的最后一块"**上，不是放在最后一块上。
2. 一次请求最多 4 个断点（Anthropic 的上限）。多打不多命中，只会抬高写入成本。
3. 断点后面必须还有可变内容；否则第二个请求根本用不上前面这段缓存。
4. **缓存是"写入 + 读取"两笔账**：写入价通常高于普通输入，读取价低一个量级。**只在预期会被复用 ≥2 次时开缓存**，一次性请求开了反而更贵。

## 5. 各家开关（先查表，别默认）

| 提供方 | 要显式开吗 | 命中怎么读 | 备注 |
| --- | --- | --- | --- |
| Anthropic | **要**：在块级/顶层打 `cache_control` | `usage` 里读/写两个缓存计数字段 | 最多 4 个断点；过期默认 5 分钟，**从请求开始计时** |
| DeepSeek | **不要**，默认开启 | `usage.prompt_cache_hit_*` / `prompt_cache_miss_*` | 按缓存前缀单元完整匹配，尽力而为 |
| OpenAI | 默认开启 | `usage` 里的缓存计数字段 | 老模型可用 `prompt_cache_*` 做路由 |

两条最容易错的迁移：

- **把 `cache_control` 抄给 DeepSeek**：它没有这个参数，写了也静默无效。
- **以为最小长度是全局常数**：不同模型的最小可缓存长度不同（常见档位 512 / 1024 / 2048 / 4096 词元）。不足时**静默不缓存、不报错**——你"开了"，但读数一直是 0。

逐家的准确数字与文档链接见 `references/providers.md`；以该表标注的核对日期为准，字段名有前缀漂移就按前缀查文档。

## 6. 命中率怎么读（自证）

- **两个缓存计数都是 0** ⇒ 本轮没命中，不要先去查网络。
- **命中率突然归零** ⇒ 先查"有没有人改了工具定义或系统提示"，这是第一大原因。
- **并发首批全 miss** ⇒ 并行的前 N 个请求里，只有最先开始响应的那个能把缓存写进去，其余全部未命中。批量任务要"先预热一条，再并发"。
- **缓存不是保证** ⇒ 过期时间从请求开始算（Anthropic 默认 5 分钟），空闲久了自然失效；DeepSeek/OpenAI 是尽力而为，缓存几小时到几天会被清理。
- **命中率高不等于省钱** ⇒ 命中部分按读取价，未命中部分按写入价（常高于普通输入）。**算的是账单，不是命中率。**

## 7. 最小可用示例

```bash
# 输入：命中词元 h、总输入词元 n；输出：词元级命中率
h=18432; n=20480
awk -v h=$h -v n=$n 'BEGIN{printf "%.1f%%\n", 100*h/n}'
```

输出：

```
90.0%
```

只依赖 `awk`：无网络、无外部文件、不依赖工作目录，放到 `/tmp` 里跑结果也一样。

## 8. 常见翻车点

1. 把"当前时间""用户本轮问题"塞进系统提示 → 命中率恒为 0，还查不出为什么。
2. 每次请求都重排工具定义或 JSON 键顺序 → 肉眼看着没改，前缀已经全变。
3. 换了 provider 还照抄 `cache_control` → 静默无效，读数全是 0。
4. 只盯命中率不看账单 → 写入价更贵，命中率低时总成本反而上升。
5. 以为"命中"是保证，没给未命中留预算 → 高峰期账单翻倍。
6. 一次请求里把所有内容都打成断点 → 写入成本拉满，命中收益为 0。

## 9. 诊断顺序（命中率不达预期时，按这个顺序查）

1. 看 usage 的两个缓存计数：是不是都为 0。
2. 抓两次请求的原始 prompt，逐字节比前缀：工具定义、系统提示、few-shot 顺序是否一致。
3. 查前缀里有没有时间戳、请求编号、随机种子、随机排序。
4. 查这段前缀是否短于该模型的最小可缓存长度。
5. 查是不是并发首批一起打进来的。
6. 以上都排除了，再怀疑服务端。

排查脚本与成本算式见 `references/diagnostics.md`。
